# 仕様書（修正版ドラフト）

## 0. 変更方針

本書は、開発開始前の仕様ドラフトです。
ユーザーとリストを独立した概念として扱い、リストへの参加者がタグとアイテムを共有する設計とします。

---

## 1. プロジェクト概要

### 1.1 アプリ名

IRU-MONO

### 1.2 目的

複数のユーザーで共有できる買い物リストアプリ。

- 買うものをリスト単位で管理する
- スマートフォンから追加・編集・完了処理を行う
- リストに参加しているユーザーが同じ内容を参照・編集できる

### 1.3 対象ユーザー

- 個人または複数人のグループを対象とする
- 一般公開を前提としない
- 1 リストあたり最大 10 人程度を想定する

### 1.4 主な利用シーン

- 日常の買い物予定の管理
- 用途ごとに複数のリストを使い分ける
- 外出先で買うものを追加する
- 買い物時に未購入アイテムを確認する
- 完了済みアイテムを一定期間後に自動整理する

---

## 2. 基本的な前提

### 2.1 ユーザー

- ユーザーは個人でアカウントを登録できる
- Google アカウントで認証する
- ユーザーは複数のリストを作成・利用できる
- ユーザーとリストは独立したエンティティとする

### 2.2 リスト

- ユーザーがリストを作成できる
- リストには名前を設定できる
- リスト作成者は他のユーザーをリストに参加させることができる
- 1 つのリストには複数のユーザーが参加できる
- 1 人のユーザーは複数のリストに参加できる
- 作成者は作成時に自動的にリストメンバーとなる
- ユーザーとリストの所属関係は `ListMember` で管理する

### 2.3 タグとアイテムの所属

- タグはリストごとに作成する
- タグはユーザーではなくリストに所属する
- アイテムもリストに所属する
- タグとアイテムは同じリストのメンバー間で共有する
- タグ名は同じリスト内で一意とする
- 個人用タグ・個人用アイテムは現時点では対象外とする

### 2.4 権限モデル

- MVP ではリストメンバーを一種類の権限として扱う
- リストメンバーは、そのリストのタグとアイテムを閲覧・編集できる
- リスト作成者は他のユーザーを参加させることができる
- 管理者・一般メンバーの細かな権限分離は今後の検討事項とする

---

## 3. 機能要件

### 3.1 ユーザー機能

- ユーザー登録
- ログイン・ログアウト
- 自分のプロフィール取得
- 認証済みユーザー自身の情報のみ取得・更新する

### 3.2 リスト機能

- リストの作成
- 自分が所属するリストの一覧取得
- リスト情報の取得
- リスト名の更新
- リスト作成者によるユーザーの参加処理
- リストからの退会
- リスト単位でのアクセス制御

### 3.3 タグ機能

- リスト内のタグ作成・一覧・更新・削除
- 1 つのアイテムに複数のタグを付与
- タグ名はリスト内で一意

例: スーパー、ドラッグストア、コストコ、百均

### 3.4 アイテム機能

- アイテム名、数量、タグを登録
- リスト内のアイテム一覧を取得
- アイテムを編集
- 完了・未完了を切り替え
- 完了日時を保持
- 未完了アイテムを手動削除
- 完了アイテムを一定期間後に自動削除

### 3.5 一覧・フィルター

- 未完了アイテムを標準表示
- 完了済みアイテムを別ビューで表示
- タグでフィルター
- 作成日・更新日・完了日時でソート

### 3.6 リアルタイム同期

- 1 人が追加・更新・削除した内容を同じリストの他のメンバーへ通知
- WebSocket を利用した同期を MVP の対象とする
- 異なるリストのユーザーにはイベントを通知しない

---

## 4. 仕様の仮決定事項

### 4.1 リスト参加方式

- リスト作成者が他のユーザーを参加させる方式を基本とする
- 招待コード・招待リンク・ユーザー指定の具体的な方式は実装前に確定する
- 招待コードは MVP では必須機能としない

### 4.2 削除ポリシー

- 未完了アイテムは手動削除できる
- 完了済みアイテムは手動削除しない
- 完了済みアイテムは 30 日経過後に自動削除する

### 4.3 認証方式

- 認証は Supabase Auth の Google OAuth に委譲する
- アプリケーションは Google のパスワードを扱わない
- セッション管理は Supabase Auth と Supabase SSR に任せる

---

## 5. 非機能要件

### 5.1 パフォーマンス

- スマートフォンでの利用を前提とする
- 一覧表示は素早く返す
- 1 リストあたり 10 人程度の利用に耐える

### 5.2 コスト

- 無料プランまたは低コスト運用を優先する
- シンプルで運用しやすい構成とする

### 5.3 セキュリティ

- HTTPS を前提とする
- Google の認証情報やパスワードをアプリ DB に保存しない
- 認証済みユーザーのみ API を利用できる
- ユーザーが所属していないリストのデータを参照・更新できないようにする

### 5.4 UX

- レスポンシブデザインを採用する
- 主要操作は 2〜3 タップ以内で完了できるようにする
- アイテムの完了切り替えはワンタップで行えるようにする
- 現在操作しているリストを明確に表示する

## 6. データ要件

### 6.1 主なエンティティ

- `User`: 個人アカウント
- `List`: 共有する買い物リスト
- `ListMember`: ユーザーとリストの所属関係
- `Tag`: リストに所属するタグ
- `Item`: リストに所属する買い物アイテム
- `ItemTag`: アイテムとタグの多対多関係

### 6.2 最小データ項目

#### User

- id
- displayName
- avatarUrl
- createdAt
- updatedAt

#### List

- id
- name
- createdById
- createdAt
- updatedAt

#### ListMember

- id
- listId
- userId
- joinedAt

#### Tag

- id
- listId
- name
- createdAt
- updatedAt

#### Item

- id
- listId
- title
- quantity
- isCompleted
- completedAt
- createdAt
- updatedAt

#### ItemTag

- id
- itemId
- tagId
- createdAt

### 6.3 データの永続性

- 過去の購入履歴を保持しない
- 完了アイテムは 30 日経過後に自動削除する
- 完了日時は削除まで保持する

## 7. API 要件（方針）

### 7.1 認証系

- GET /auth/callback
- POST /auth/logout
- GET /auth/me

### 7.2 リスト系

- GET /lists
- POST /lists
- GET /lists/:id
- PUT /lists/:id
- DELETE /lists/:id
- POST /lists/:id/members
- DELETE /lists/:id/members/:userId

### 7.3 タグ系

- GET /lists/:listId/tags
- POST /lists/:listId/tags
- PUT /lists/:listId/tags/:id
- DELETE /lists/:listId/tags/:id

### 7.4 アイテム系

- GET /lists/:listId/items
- POST /lists/:listId/items
- PUT /lists/:listId/items/:id
- PATCH /lists/:listId/items/:id/toggle
- DELETE /lists/:listId/items/:id

### 7.5 レスポンス方針

- 成功時は統一した JSON 形式を採用する
- 失敗時は `error` と `code` を返す
- `401`、`403`、`404`、`409`、`422` を適切に使い分ける

- ログ記録
