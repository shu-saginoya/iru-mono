# プロダクト仕様（MVP）

## 1. 目的

複数のユーザーで買い物リストを共有する。初回リリースは、迷わず使える最小機能に絞る。

- Google アカウントでログインする
- ユーザーがリストを作成する
- リストのメンバーがアイテムを共有する
- アイテムを追加・編集・完了・削除する

## 2. 基本モデル

### User（ユーザー）

- Google アカウントで認証する
- 複数のリストを作成・利用できる

### List（リスト）

- ユーザーが名前を付けて作成する
- 作成者は自動的にメンバーになる
- 1 つのリストに複数ユーザーが参加できる
- 1 人のユーザーが複数リストに参加できる

### Item（アイテム）

- リストに所属する
- 商品名、数量、完了状態、完了日時を持つ
- 同じリストのメンバー間で共有する
- タグ、カテゴリ、優先度、担当者は初回リリースでは持たない

### ListMember（リストメンバー）

- ユーザーとリストの所属関係を管理する
- 初回リリースでは全メンバーを同じ権限として扱う
- 作成者だけがメンバー追加とリスト削除を行える

## 3. 機能要件

### 認証

- Google OAuth によるログイン
- ログアウト
- 自分のプロフィール取得

### リスト

- リスト作成
- 自分が所属するリストの一覧取得
- リスト名の変更
- リスト情報とメンバーの取得
- 作成者によるユーザー追加・メンバー除外
- 自分の退会
- 作成者によるリスト削除

### アイテム

- アイテム作成
- アイテム一覧取得
- アイテム名・数量の編集
- 完了・未完了の切り替え
- 未完了アイテムの手動削除
- 未完了を標準表示し、完了済みも切り替えて表示できる
- 作成日または更新日の新しい順で表示する

## 4. 対象外

- タグ・カテゴリ・検索・優先度・担当者
- 招待コードや招待リンク
- リアルタイム同期
- 完了アイテムの自動削除
- 通知、監査ログ、複雑な権限管理
- 購入履歴や分析

画面内の更新は再読み込みなしで反映する。他ユーザーの変更はリアルタイム同期しない。追加機能は必要性を確認してから決める。

## 5. 非機能要件

- 認証は Supabase Auth のセッションを利用する
- リストの所属確認を API と Supabase RLS の両方で行う
- サービスロールキーをブラウザへ渡さない

詳細は [API仕様書](API_SPEC.md) と [DBスキーマ](DB_SCHEMA.md) を参照する。

## 6. 保留事項

- 招待方法は、初回は作成者によるユーザー ID 指定とする
- 作成者と一般メンバーの権限分離は後回しにする
- リスト作成者の退会・譲渡フローは後から決める
